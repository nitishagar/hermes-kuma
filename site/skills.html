Skills

Four workflow skills. They share one discipline: read-first, never the delete tools, and explicit confirmation before any write.

Read-first: these workflows use read tools by default; the only writes they may ever perform are pause, resume, and maintenance windows — and only after you explicitly confirm the specific action.

Never the deletes: deleteMonitor, deleteNotification, deleteDockerHost, deleteTag, deleteStatusPage are permanent and have no upstream confirmation gate; this bundle's workflows do not use them.

kuma-setup

Use when connecting, configuring, authenticating, or debugging Uptime Kuma access.

Credential tiers (see Credentials), the first-connection check, the troubleshooting ladder (Node version → cold npx cache → missing env vars → wrong credentials → unreachable instance), and the hard limits: Uptime Kuma v2 only, alerting stays in Kuma's own channels.

kuma-incident-review

Use when something is down or degraded and you need to understand what happened.

Starts from the monitor summary (“how is everything?”), pulls the heartbeat timeline for the affected monitor, and drafts a structured incident summary. Summary-first: no per-monitor crawling to answer a fleet question.

kuma-status-digest

Use for a periodic fleet-wide uptime digest.

Produces overall posture from one summary read — what's up, down, or paused — annotated with scheduled maintenance windows. Same read discipline as incident review, tuned for reporting rather than diagnosis.

kuma-maintenance

Use to pause/resume monitoring or schedule downtime for planned work.

The only skill with a write surface, and every write needs your explicit yes after the agent restates the exact action:

  1. Pause a monitor — for planned work or noise suppression. A paused monitor stops alerting entirely.
  2. Resume a monitor — then watch the first heartbeat and report whether it's actually back.
  3. Schedule a maintenance window — monitors, start, duration/strategy, title; duplicates get called out instead of created.

Everything else write-like (create/update monitors, notifications, tags, docker hosts, status pages) routes you to the Kuma UI — that is the correct answer, not a refusal to be worked around.

When MCP is unavailable

The skills double as guides: follow their steps against the Kuma web UI (or a pasted status page) and produce the same structured output. The agent says plainly that live reads are unavailable and never invents monitor states; writes are impossible without the connection, so confirmed-but-unapplied actions get queued explicitly instead of simulated.
